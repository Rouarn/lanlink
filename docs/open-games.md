# 房间内「开放游戏」宣告协议

> 状态：v1 已冻结。任何字段变更都必须提升协议版本号，不能复用同名端口做不兼容修改。

## 1. 目标与边界

房间里的任意成员在本机开着局域网游戏时，其他成员应当能在 LanLink 里直接看到：

- 谁开的（房间内的设备名 / 虚拟 IP）；
- 开的是什么（游戏名或《我的世界》世界名）；
- 端点是多少（`虚拟IP:端口`），可一键复制进游戏的直连 / 添加服务器输入框。

这一层**不解析具体游戏协议**，只搬运「某人正在某个端口上开放游戏」这一事实，是后续自动发现能力的底座。

v1 的本机游戏来源只有两种：

1. `lan.rs` 已经解析到的《我的世界》Java 版局域网公告（MOTD + AD 端口）；
2. 用户在房间页手动登记的「游戏名 + 端口」。

不做进程扫描、不做 DLL 注入、不做其他游戏的协议识别。

## 2. 通道选型：单播，不用广播/组播

**结论：UDP 单播，固定端口 4449，只发给 `easytier-cli peer` 里出现的对端虚拟 IP。**

原因：

- EasyTier 的 TUN 不保证转发广播 / 组播，`lan.rs` 对《我的世界》的跨端同步也已经选择单播，继续复用同一条经验；
- 单播可以天然拿到**真实的 overlay 源地址**，来源校验不需要从载荷里读取任何自报 IP；
- 房间成员数量很少（个位数），逐个单播的成本可以忽略；
- 不引入新的外部二进制或依赖，仍然只使用 Rust 标准库 + `socket2`（项目已有）。

不使用的方案：

- 不走 `224.0.2.60:4445`（《我的世界》组播地址，语义不同，还会干扰原版客户端）；
- 不借用 `broadcast.rs` 的端口表（那是有状态的游戏报文搬运，需要防回灌、按端口转发，语义和生命周期都不同）；
- 不占用 4448（`lan.rs` 的《我的世界》世界同步端口）。

## 3. 端口与报文

| 项目 | 取值 |
| --- | --- |
| 传输层 | UDP |
| 端口 | `4449` |
| 方向 | 仅单播到对端虚拟 IP，不广播、不组播、不经中继服务器 |
| 编码 | UTF-8 JSON，单包上限 4096 字节 |

报文：

```json
{
  "lanlink": 1,
  "channel": "open-games",
  "network": "lanlink-8k3m",
  "games": [
    { "port": 25565, "name": "Steve - My World", "source": "minecraft" },
    { "port": 27015, "name": "CS 1.6", "source": "manual" }
  ]
}
```

字段说明：

- `lanlink`：本通道协议版本，当前为 `1`；版本不符直接丢弃。
- `channel`：固定 `"open-games"`，用于避免误解析其它端口上的 JSON。
- `network`：房间网络名（`lanlink-*`），必须与接收方当前房间一致，否则丢弃。
- `games`：**完整快照**，不是增量。每项：
  - `port`：1–65535，0 与 LanLink 自用端口（4445 / 4448 / 4449）会被发送方过滤，接收方也会再过滤一次；
  - `name`：显示名，折叠空白后最多 48 个字符；为空时由接收方回退为「局域网游戏」；
  - `source`：`"minecraft"` / `"manual"` / 空字符串（未知来源），仅用于界面标注，不参与信任判断。

载荷中**没有 IP 字段**。端点一律由接收方用「真实源 IP + 报文端口」拼出，从协议层消除「载荷自报 IP」这一攻击面。

## 4. 发送节奏、TTL 与去重

- 发送频率：每 **2 秒**一次，连上房间后立即播一次。
- 静默 TTL：**18 秒**（约 9 个周期）。超过 18 秒没再收到某个对端的报文，直接移除该对端的所有游戏。
- 空列表：发送方即使没有游戏也继续发空快照；接收方需要**连续 3 次**空快照才清空该对端的列表（约 6 秒），避免游戏重启 / 短暂关服导致列表闪烁。
- 非空快照：收到即**整体替换**该对端的游戏集合，不保留旧条目；配合 TTL 处理对端整机掉线。
- 去重维度：`(源虚拟 IP, 端口)`。同一端口以最新一条报文为准；端口相同的手动登记与《我的世界》自动发现，在发送侧由自动发现覆盖（世界名更准确）。
- 限制：每包最多 16 个游戏、名字最多 48 个字符、包长最多 4096 字节；超限条目直接截断，不拆包。

## 5. 来源校验与防欺骗

接收一条报文时按顺序校验：

1. 源地址必须是 IPv4；
2. `network` 必须等于本机当前房间网络名；
3. `channel == "open-games"` 且 `lanlink == 1`；
4. 源 IP 必须是 `easytier-cli peer` 快照里的对端虚拟 IP，且不能是本机地址；
5. 对端列表暂时为空时（刚连上、CLI 短暂失败），退化为「私有网段且非本机」兜底——与 `lan.rs` 现有策略一致；
6. 报文里的 `port` / `name` / `source` 只作为展示数据，**不信任任何地址声明**。

界面展示和复制用的端点永远是 `真实源 IP:端口`，不是报文内容。

EasyTier 本身已经对 overlay 流量做了加密与节点认证；本协议不再额外做签名/MAC，避免重复造轮子。

## 6. 房间隔离

- 每个房间使用独立的 EasyTier 网络名与密钥，overlay 地址空间天然隔离；
- 报文只单播给当前房间的 peer，不做任何广播；
- 报文显式携带 `network` 并做严格比较，防止切换房间后旧 peer 快照或残留报文串台。

## 7. 与既有能力共存

| 模块 | 端口 | 关系 |
| --- | --- | --- |
| 《我的世界》组播发现 | `224.0.2.60:4445` | 本机世界来源之一；`lan.rs` 解析后写入共享的本机游戏表 |
| 《我的世界》跨端同步 | `4448` | 完全独立，互不读写 |
| 通用 UDP 广播转发 | 用户端口表 | 只搬运游戏报文，不碰 4449；`broadcast.rs` 的端口规整会排除 4449 |
| 开放游戏宣告 | `4449` | 本文件描述的通道 |

- 三个中继共享 `core` 维护的同一份 peer 虚拟 IP 快照，不额外起 `easytier-cli` 进程；
- `core.rs` 只负责启动/停止生命周期，`games.rs` 不解析任何游戏报文；
- `broadcast.rs` 的 `normalize_ports` 排除 4445 / 4448 / 4449，避免用户把协议端口填进广播表。

## 8. 降级策略

| 场景 | 表现 |
| --- | --- |
| 房间码解析服务不可用 | 本通道完全不依赖解析服务，已连接的房间照常工作；加入房间本身可能失败，那是既有流程，不在本通道范围内 |
| `easytier-cli peer` 暂时拿不到对端 | 不发送（没有目标），界面显示「等待对端」；本地游戏仍在本机列表里 |
| UDP 4449 绑定失败 | 本通道停用，卡片显示失败原因；房间创建、加入、虚拟 IP、日志等其余功能不受影响；30 秒后自动重试 |
| 局域网发现被关闭 | 《我的世界》自动来源消失，手动登记仍然有效；本通道本身不随该开关关闭 |
| 某个对端静默 | 18 秒后自动从列表移除，不阻塞其他对端 |
| 对端发来空列表 | 连续 3 次才清空，避免闪烁 |

## 9. 本机采集（v1）

- 《我的世界》：复用 `lan.rs` 的 `WorldTracker` 结果（端口 + MOTD），通过共享的本机游戏表交给 `games.rs`；
- 手动登记：`settings.json` 中的 `manual_games`，形如 `{"name":"CS 1.6","port":27015}`，随设置原子落盘；
- 手动登记端口与 `broadcast_ports` 相互独立：一个只负责「展示 + 复制地址」，一个负责「搬运广播报文」。

## 10. 界面契约

`get_status` 增加：

```ts
open_games: Array<{
  name: string;
  hostname: string; // 开游戏的人；本机为设备名
  ipv4: string;     // 端点 IP（真实源 IP 或本机虚拟 IP）
  port: number;
  source: string;   // "minecraft" | "manual" | ""
  mine: boolean;    // 是否本机开放
}>;
games_relay: boolean;      // 宣告通道是否运行
games_error: string | null; // 启动 / 运行失败原因
```

新增命令 `set_manual_games(items)`：保存手动登记表并立即生效，返回最新 `Status`。
